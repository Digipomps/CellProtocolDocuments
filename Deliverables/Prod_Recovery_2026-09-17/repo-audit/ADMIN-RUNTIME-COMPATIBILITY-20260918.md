# Admin runtime compatibility: frozen web candidate versus running admin revisions

Read-only source review, 2026-09-18. Production baseline `74c7a57f7b842510d07048418fa845a286100594`; staging baseline `f76de5a984501cb4d67e275c892d62ce3fc348c7`; frozen candidate `f26c16fe4b7cc999895f26f9959af2d2181cd168`. Their CellProtocol pins are respectively `1632ed65`, `135d3c00`, and `533b42d5`. No builds, tests, network, SSH, source/runtime/Git mutations performed. [Blob and changed-path evidence](admin-runtime-compatibility-evidence.json). Root's [redacted host inspection](/private/tmp/haven-prod-20260917/admin-topology-redacted.json) confirms both old images running/healthy, read-only root filesystems and one writable storage bind each; health is not remote-admin acceptance evidence.

**Decision: deploy the web candidate, then include a separate admin rollout in the recovery. It is not a prerequisite for the ordinary Butler thread GUI or the new web mandate cells; it is necessary before declaring the complete remote-admin path fixed and secure.** No AdminEntry/AdminOverview/control-plane call was found in the inspected Butler thread, gateway and personal-chat implementations. The mandate cells are App/Run code, whereas AdminScaffold depends on ScaffoldKit only ([target split](/private/tmp/haven-prod-20260917/CellScaffold/Package.swift:267)). The existing [rollout plan](ADMIN-IMAGE-ROLLOUT-PLAN-20260918.md) remains the deployment-mechanism assessment; this report does not implement or invent a controller.

## Existing signed snapshots remain compatible

Git blobs are **identical across all three revisions** for bridge HMAC authentication, NodeAdminAgentSnapshotTrust, NodeAdminAgentSnapshotBuilder, AdminNodeFleetCell, NodeAdminAgent and NodeAdminDockerCollector. The corresponding signed-envelope, ingest and delivery test files are also identical. Therefore this release requires neither a node-tool update for format compatibility nor new signing keys/HMAC keys. HMAC bridge authentication and Ed25519 node envelopes are separate contracts.

Preserve the owner, trusted-key set, node signer, sequence state and persisted snapshot store. A fresh envelope from an old node executable remains format-compatible; this does **not** permit replaying an old envelope. Sequence must increase, timestamps must satisfy skew/TTL bounds, and expiry still rejects stale input. [Unchanged validation](/private/tmp/haven-prod-20260917/CellScaffold/Sources/ScaffoldKit/NodeAdminAgentSnapshotTrust.swift:293). Retained expired records may be displayed as stale, not represented as fresh readiness evidence.

Production also changes startup behavior: `ADMIN_SCAFFOLD_STARTUP_MODE`/load-only handling present at `74c7a57f` is removed in the candidate (staging already has the candidate behavior), and bootstrap is a separate executable. Root's topology confirms production still has the old environment variable. Do not assume that variable enforces load-only behavior after upgrade. Preserve and validate existing manifest, owner and storage; keep a compatible storage backup with rollback. This is a migration concern, not a snapshot-schema migration. The two containers also use different Unix users, so unchanged mounts alone do not prove candidate write access.

## Test evidence and remaining acceptance

The source has meaningful tests for signed-envelope requester binding, tampering, expiry/replay, persistence-failure rollback and trusted-key ingest ([snapshot tests](/private/tmp/haven-prod-20260917/CellScaffold/Tests/AppTests/NodeAdminAgentSnapshotBuilderTests.swift:152), [ingest test](/private/tmp/haven-prod-20260917/CellScaffold/Tests/AppTests/AdminScaffoldSnapshotIngestTests.swift:10)). The ingest test exercises the store directly, not a live HTTP endpoint.

`AdminEntryRemoteBridgeLoopbackTests` starts an AdminScaffold process, uses dedicated bridge routing and asserts a real remote `verifyEntryCredential` response plus client proof verification. It creates isolated state, permits owner creation and disables trusted/fresh-node readiness requirements. Normally it uses the build's companion AdminScaffold executable, with an explicit binary override supported. **It does not establish candidate-web/old-admin compatibility or prove the complete AdminOverview user flow.** [Process/setup](/private/tmp/haven-prod-20260917/CellScaffold/Tests/AppTests/AdminEntryRemoteBridgeLoopbackTests.swift:49), [remote assertion](/private/tmp/haven-prod-20260917/CellScaffold/Tests/AppTests/AdminEntryRemoteBridgeLoopbackTests.swift:155). Multiplex tests establish route parsing/defaults, not live cross-version interoperability. No test pass is newly claimed by this audit; root owns the ongoing Linux CI evidence.

After the admin image upgrade, the remaining meaningful acceptance is remote AdminEntry **and** AdminOverview from the deployed web through the real authenticated route, refusal with invalid credentials, unchanged owner/manifest after restart, and a fresh accepted envelope from the existing node agent with preserved sequence. These checks close the identified server/proof gap. A healthy old admin container alone does not close it.
