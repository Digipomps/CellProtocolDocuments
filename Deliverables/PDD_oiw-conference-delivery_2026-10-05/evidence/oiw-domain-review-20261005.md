## Actionable findings

1. **P1 — stale intention writes can restore discoverability after an opt-out.** `ConferenceCommonsState.swift:141–150` stores an intention revision but accepts no expected revision. Two views read revision 1 with `discoverable=true`; A saves false (revision 2); B submits an older purpose edit containing true and the method restores discoverability (revision 3). `matches` immediately exposes that record again (`157–172`). Serialization only determines which stale write wins. Add a revision precondition, or separate explicit discoverability consent from general profile writes; reject stale changes without replacing the record. Suggested verification: retain false after the exact interleaving above.

2. **P2 — stop can invalidate approvals without invalidating their version.** `stopMeeting` accepts an already stopped/reviewed meeting, clears `reviewApprovals`, but advances only the plan revision (`274–279`). `approveReview` checks the unchanged `reviewRevision` (`305–311`). Thus delayed approvals for review v1 can restore approvals after a subsequent stop cleared them. A delayed duplicate stop can also erase valid approvals after review began. Make ordinary stop idempotent once stopped and restrict its valid source phases; if clearing review consent is an intended operation, advance its consent/review generation so earlier requests become stale. Full `revoke:true` already blocks later approvals through `ownMeeting`; this finding concerns the false branch, not a bypass of full revocation.

3. **P2 — a partial booking eliminates all remaining free time from matching.** `matches` computes the whole availability intersection, then discards it on any booking overlap (`162–168`). Example: both available 10:00–12:00, one reserved 10:00–10:30; the model returns no match despite 90 free minutes. Subtract the union of both participants' reservations before filtering for minimum duration, then normalize/deduplicate slots. Preserve `approveMeeting`'s conflict check as the authoritative reservation check (`247–258`). Suggested verification: matching returns 10:30–12:00 while confirmation still rejects overlapping reservations.

## Required integration contracts — not claims of bugs in an absent Cell

- **A serialized transaction must span candidate creation, persistence and publication of new state.** Lines 5–7 and 251–252 correctly delegate this to the host. An actor alone does not suffice if it releases isolation across `await persist(candidate)` and another request derives a candidate from old state. Use the established non-reentrant queue/transaction or revision CAS; acknowledge only after durable commit. Resolve proven requester separately from payload IDs. Boolean publisher rights must be computed for the exact publisher/event/umbrella being acted upon and remain current at the effect boundary. Recheck after external waits; never replace the requester with the owner's identity.

- **Define what `.conference` authorizes before exposing reads/export.** `visibleContributions` permits every supplied requester to read every conference contribution in the requested umbrella (`222–225`); `exportContribution` ignores requester and checks only audience, revision and withdrawal (`331–335`). This is consistent only if published conference contributions are intentionally readable by everyone admitted to this Cell surface. If `.conference` means a restricted conference/umbrella audience, the Cell must resolve that scope for every list/read/export. Authentication alone is insufficient. Never expose the Codable state or raw `meetings`/`intentions` dictionaries as a client snapshot.

- **Expiry needs a real host action and filtered reads.** `ownMeeting` blocks operations after retention (`349–352`), but persisted text is erased only when `expireMeetingContent` runs and its candidate is committed (`338–345`). Call it at hydration/action/read boundaries and arrange cleanup during idle periods if time-based deletion is promised. Its intentionally independent publication lifecycle is defensible: meeting expiry does not withdraw an approved public contribution. The review UI must make that difference explicit; a seven-day meeting retention value must not imply seven-day publication retention. Direct contribution withdrawal remains available after meeting expiry (`210–218`).

- **WP5 export needs an immutable provenance/consent envelope beyond the returned Contribution.** The meeting export currently contains the publishing clicker's `author`, `meetingID`, and contribution revision 1 (`320–325`); it omits the approved review revision, co-approvers and their exact audience mandate. These remain only in the source Meeting and are cleared on expiry (`341`). Before portable delivery, preserve an immutable publication record tied to content/source version, approval generation and permitted audience (or an owner-controlled auditable reference with an explicit lifetime). Add source authority/namespace and the receiver's exact grant/operation ID to the transport envelope; a bare host-local ID and revision are not globally unique. This does not require a new transport protocol. Avoid exporting participant identities beyond the explicitly approved provenance scope.

The strongest existing boundaries are worth preserving: private drafts are author-only; publishing a single-author draft requires its author and exact revision; meeting publication requires both approvals for the same text revision and audience; publication cannot edit the approved text; withdrawal erases text and rejects new exports; reservation checking is requester-specific across meetings. These conclusions are static source observations, not passed tests. The three concrete findings can be fixed without broadening protocol scope.
