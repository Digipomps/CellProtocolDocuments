## Blockers

1. **P1 — deleting assignments resets the generation and defeats stale-revoke protection.** Candidate lines 81–86 remove the row; lines 47–55 use `old?.revision ?? 0` on a later grant. Sequence: grant B at revision 1; revoke B(1); regrant B becomes revision 1 again; delayed revoke B(1) removes the new grant. This contradicts the comment at 71–72. Moreover, `expectedRevision` is optional on `setMemberAccess` (48–49), so a delayed legacy grant can recreate a removed membership or restore old permissions after revocation. Retain a revoked tombstone or a monotonic per-assignment epoch, and require the observed epoch for bound/managed grants and renewals. Do not allow the legacy setter to mutate those managed assignments without that precondition. Operation-ID reconciliation is needed if retries are to receive a reliable prior result.

2. **P1 — the persistence ACK is not evidence that revocation reached storage.** Candidate lines 105–110 return `revoked` based on `persistCellSnapshot`. At the pinned CellProtocol ref `81601a6f835252aba7e99d43786fb5d67227c245`, `Sources/CellBase/Cells/CellResolver/CellResolver.swift:553–592` calls the void typed-store API and then returns true. The matching inspected integration source `Sources/CellBase/PersistingCells/TypedCellsUtility.swift:96–109` catches storage errors and only logs them. Thus disk-write failure can produce a success ACK and resurrect the old grant after restart. Use a verified persisted read-back of the exact generation/tombstone before success, as the pending Commons Cell already attempts, or a storage API with a real failure result. On uncertainty, retain a fail-closed local revocation and an explicit recoverable reconciliation state; the current retry merely sees “stale” because its assignment was deleted.

3. **P1 — no mutation/persistence transaction; existing encoder reads outside the queue.** Candidate revoke releases `stateQueue` at line 90 before awaiting snapshot persistence at 106. Other setMemberAccess/event/profile writes remain available. Existing `EventPublisherRegistryCell.swift:47–52` directly encodes all three mutable containers without `stateQueue`, while the mutation methods use that queue. The added explicit snapshot path therefore runs against mutable state with no coherent snapshot or per-cell write ordering. At minimum copy all persisted fields under the queue for encoding, then serialize candidate mutation, persistence/read-back, and ACK across grant/revoke operations. Account for lifecycle persistence too. Merely placing the synchronous row removal in `stateQueue.sync` does not make the async durability boundary atomic. This is an existing encoder weakness exposed by the new promised ACK, not a defect introduced by optional Codable fields.

4. **P1 for the claimed bound-authority boundary — the legacy setter can manufacture the bindings the new surface trusts.** Candidate line 45 deliberately authorizes grant/key replacement using the default UUID-only-compatible evaluator; lines 41 and 54 accept an arbitrary fingerprint. A legacy unbound manager can bind itself or another identity, after which Commons treats that binding as strict authority (114). Therefore a nonnil fingerprint is not, by itself, evidence of a trusted migration or cross-domain mandate. Keep old setters for old unbound records, but define a separate trusted binding/migration path (current verified account/domain authority or an already bound manager) and prevent legacy calls from overwriting managed bound credentials. This is not an assertion that a browser attacker can currently spoof an authenticated account; the problem is that the registry API does not establish the stronger claimed boundary.

5. **P2 — last-manager protection counts managers that cannot use the strict surface.** Candidate lines 57–58 and 83 accept any non-expiring assignment with `manageMembers`, including unbound ones. Add unbound B as permanent manager, then revoke bound A: accepted, but no remaining manager satisfies `revokeMember(requireBoundKey:true)` or Commons. Arbitrary unusable fingerprints can also count as the last permanent manager. Preserve the existing generic last-manager invariant, and for a publisher activated for bound operations additionally preserve at least one usable bound permanent manager; don't rely on the unsafe legacy self-binding escape above. Key replacement of the final bound manager needs a deliberate proof/rotation path.

## Compatibility and operability

- Candidate lines 3–20 are largely well scoped: missing legacy fields decode to nil/nil/revision 1; legacy role-to-permission decoding remains; nil expiry and nil binding retain old evaluation when `requireBoundKey=false`. Once fields are populated, even default evaluation enforces their expiry/key. That is sensible but should be described as preserved behavior **for legacy records**, not universal unchanged semantics.
- Automatically binding all new publisher creators (23–27) changes how alternate identities/keys with the same effective UUID work. It should ship with the binding/rotation decision, not be hidden inside a compatibility patch. `createPublisher` still allows a nil fingerprint; strict Commons would then reject the new creator. Require a proven nonnil binding for the strict creation path.
- Required revisions are currently not observable through normal read projections: `loadPublisherState` member rows at `EventPublisherRegistryCell.swift:318–328` contain no assignment revision/expiry/binding status; Commons member rows at `ConferenceCommonsCell.swift:285–289` hardcode revision 0. Expose the current revision and active/expired state to authorized managers before enabling the revoke UI. The candidate adds a registry action but no Commons company mutation action.
- Expiry cannot be cleared through the proposed parser: `EventPlatformValueDecoding.string` trims blank to nil (`EventPlatformModels.swift:271–279`), while candidate line 53 interprets nil as “preserve old expiry.” Use an explicit clear-expiry operation/value if renewal to a permanent assignment is intended. Expired rights do correctly stop being counted by the new evaluator at call time.

Suggested verification after the authorized build gate: legacy decode/role behavior; expiry boundary; wrong bound key; final usable manager; revoke/regrant/delayed revoke; stale legacy grant after revoke; disk-write failure plus restart; concurrent mutation and persistence; observable revision and lost-response reconciliation. None was executed in this review.
