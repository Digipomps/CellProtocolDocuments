Two concrete integration hazards should be handled before reusing the native UI pattern for consent-sensitive actions:

1. `NearbyScannerSurfaceView.swift:29–38` resolves the local scanner with the vault's `private` identity. `ConferenceNearbyRadarSurfaceView.swift:341–360` similarly obtains the local private identity. This is a local device-owner path; it must not silently become the requester for a guest's remotely loaded meeting action. Show and bind the real active participant identity and keep local hardware authority separate from meeting/publication authority.
2. `NearbyScannerSurfaceView.swift:55–65` rejects selected string failures but otherwise reports success, including a nil result. For capture, sharing, saving or deletion, a missing/unknown reply must be an unknown outcome with reconciliation by operation ID, not success or automatic retry.

## Proposed minimal portable UI contract — all new meeting elements unimplemented

Keep nearby scanning **Binding-only**, as requested. Web may display a truthful unavailable state and the separately authorized meeting/review surface, but must not render a working-looking Scan button backed by fixtures. Proximity, transport connection, verified participant identity, meeting membership, recording approval and publication approval are distinct visible states.

No new Skeleton element is required to propose the basic journey. Compose existing `VStack`, `HStack`, `Section`, `Text`, `List`, `Button`, `TextArea`, `Toggle`/`Picker` and optional `Tabs`. `SkeletonDescription.swift:4160–4186` supports these. Avoid depending on nested remote ComponentSurface features until their named adapter gaps are resolved. Any waveform is optional visualization, never the source of recording truth.

Proposed read model, not implemented keypaths:

- `meeting.state`: opaque session reference, domain, exact participant set/version, active requester, host, recorder, current phase and last acknowledged operation.
- `meeting.plan`: version/hash; declared purposes; audio source; transcription/model route and recipients; fields proposed for extraction; per-material retention; separate capture/transcription/review-sharing/publication/storage choices.
- `meeting.participants`: participant handles and membership/proof state; signed approval for the exact plan; current capture lease/connection state; no blanket public identity linkage.
- `meeting.capture`: `off | awaitingApproval | ready | recording | paused | stopping | stopped | remoteStatusUnknown | failed`, reason, recorder identity, elapsed time and last acknowledgement. Show persistent recording status and Stop for every authorized participant.
- `meeting.review`: immutable transcript versions, time/source references, uncertain speakers, corrections/disputes; metadata and shared-purpose proposals each retaining source, author/model provenance and participant acceptance state.
- `meeting.disclosure`: selected version/excerpts, exact named recipients/audience, per-participant approvals and separate operation/delivery receipts. A private share is different from publication on the conference/public web.
- `meeting.retention`: permission and receipt per destination/user; material expiry, requested deletion, confirmed deletion and unknown remote-copy status. Do not use one green check for both users' saves.
- `meeting.capabilities`: separately sourced flags/reasons for nearby scan, capture, local transcription, remote processing, review, share, publish and store. Capability absence remains visible and prevents action; UI hiding is not authorization.

Proposed actions, all unimplemented as a combined contract: invite/accept/refuse/leave participation; propose/approve/reject a plan; start/pause/stop capture; submit correction/dispute; approve an immutable review version; share exact selected fields; publish exact selected fields to an exact audience; store chosen output in one's own Entity; revoke/withdraw; read receipts. Every write requires session, actor, plan/version and idempotent operation binding and explicit typed outcome.

Native capability boundary: Binding owns OS permissions, microphone/AVAudioEngine lifecycle, optional on-device recognition, foreground/background/audio-route/interruption handling, nearby discovery/ranging and local key use. Native adapters report actual results into the Cell state; they do not infer another party's consent. Portable Cells own meeting membership, plan transitions, operation authorization, review versions, publication/storage decisions and receipts. Resolver/Cell authorization remains authoritative on every action, including host-owner actions; an app shell, link or transport session grants no additional authority. Shared Bridge integration must be proven for both setup and subsequent Cell operations, not replaced by a new person-specific callback route.

## Proposed state machine — not implemented

| State | Entry and allowed actions | Required transition/check |
| --- | --- | --- |
| Discovered | Show minimal elected excerpt and disclosure status; request connection/contact | Beacon/nearby overlap is a hint, not a participant identity, invitation acceptance or recording approval. |
| Participation pending | Named invitee can accept/refuse; initiator can cancel | Bind exact session/domain, both operational identities, proof path and visible host. Refusal ends this attempt without repeated prompts. |
| Joined, no recording | Both may talk, leave or propose capture; no microphone starts automatically | Participation alone grants no recording/transcription/model/publication/storage permission. |
| Plan pending | Both review same version/hash and decide; each technical capability reported separately | Bind participant set, purpose, recorder/source, processor/location/recipients, output selection and retention. Require all necessary signatures for exact plan and fresh grants. Reject stale version or host-owner bypass. |
| Ready | Both approvals valid; microphone permission/adapter ready; current participant/contact lease confirmed | Only explicit Start for the approved recorder. Recheck at native effect, not only before an await. Local grants cannot impersonate remote approval. |
| Recording | Persistent indicator on both sides; either may Pause/Stop | Immediate local stop on stop/revocation, participant change or capability loss. Remote stop has its own acknowledgement and unknown state. Connection loss suspends capture by a pre-agreed bounded heartbeat/lease deadline; no indefinite offline continuation. |
| Paused / authority changed | Show cause and actual recording status; continue conversation without capture | New participant, changed host/model/recipient/purpose or plan version invalidates affected approvals. Resume only after the necessary renewed decisions. App cannot detect every physical bystander; provide explicit add/pause control and a visible reminder. |
| Stopped / processing pending | Freeze actual captured span; run only processing that the current plan permits | No external model transfer or persistent raw-audio storage inferred from capture approval. A crash/restart does not resume recording automatically. |
| Review | Participants correct, exclude or dispute transcript/speaker attribution; inspect provenance | Produce immutable new versions; edits invalidate prior version-specific acceptance. Inferred themes/interests remain proposals, not accepted personal facts or shared purposes. |
| Private sharing pending | Choose exact version/excerpts/metadata/purposes and named recipients | Each affected participant approves the exact output manifest and recipient set. Their receipt attests approval, not the factual truth of a transcript. |
| Shared / partly delivered | Show per-recipient receipt and retry/reconcile by exact operation ID | Delivery to one person does not prove delivery/storage at another. Store in each person's Entity only under that person's scoped storage authority and selection. |
| Publication pending / published | Optional, separate action choosing public/conference audience | Sharing with the two participants does not authorize public conference/profile publication. Recheck exact content/version/audience approval at publication. |
| Revoked / closed / deletion pending | Stop future authorized collection/processing/disclosure; retain minimal truthful receipt trail per policy | Revocation cannot prove removal of already revealed copies. Distinguish withdrawn publication, remote acknowledgement, expired authorization, requested deletion, confirmed deletion and unavailable/offline recipient. |

The five-minute scanner excerpt lease is unsuitable as an implicit meeting recording lease; this requires its own declared revocation and interruption semantics.

## Failure and threat acceptance required before a real meeting pilot

All meeting-specific tests below are proposed, not run. Existing source tests may supply useful fixtures but do not satisfy the complete acceptance row.

| Case | Required observable result / test |
| --- | --- |
| New participant / audible bystander | Membership change pauses actual capture before new samples are admitted; old plan cannot resume it. Explicit physical add/pause flow acknowledges people the app cannot detect. Third device cannot join by reusing a participant UUID. |
| Refusal | Decline meeting still permits no access; decline recording leaves voluntary conversation available, with no capture or repeated consent/authentication prompts. Permission-denied OS state is distinct from another person's refusal. |
| Offline / host disappears | Local stop is immediate; remote status is unknown until acknowledged; capture expires at the declared contact lease. Restore never auto-records. Approved prior transcript can be reviewed offline only within its existing grants; publication waits for verifiable current authority. |
| Grant revoked during suspended work | Hold work after initial authorization and before microphone start, model transfer, store and publish effects; revoke, release barrier and prove zero forbidden effect. A discarded late UI response alone is insufficient. |
| Guest crossover | Guest cookie/link/public catalogue access cannot become local `private` owner identity; attendee and guest in different domains cannot access each other's meeting, draft, proof or audio. Swap requester, tab, endpoint and session IDs. Test denied paths through actual Resolver and browser/native host. |
| Replayed/stale approval | Replay valid signature on a new session, changed participant set, changed plan/processor/audience or different version; reject. Preserve a fresh valid path. Bind wire-canonical bytes/digests and actual signer, not only UUID. |
| Native mic / route/background failure | Test denied/revoked OS permission, unsupported locale/on-device recognition, incoming call, Bluetooth route change, lock/background, power loss; portable state reflects actual capture and no silent restart. |
| Lost response / duplicate submit | Drop acknowledgement after an effect; show unknown, reconcile exact operation ID, prove no second capture/job/store/publication. Explicitly test current nil-success UI helper cannot be reused. |
| Unagreed transcript or metadata | One party disputes speaker or purpose attribution; prevent publication under prior acceptance. Keep source quote, model inference and accepted normalized value separate. No automatic Entity enrichment from topic mention. |
| Retention / misleading release receipt | TTL expiry alone does not claim deletion; trace actual backend deletion and offline copies separately. TranscriptStore release result is not recipient delivery. Test missing `s`, absent sharing capability, changed recipient and independent durable saves. |
| Transport / radio abuse | At least two real devices plus a third adversarial peer: invitation refusal, nonce/session mix-up, reconnect/late message, loss/retry, floods and sustained queues, with sibling isolation and real physical disconnect. Report observed radio/device limits, not synthetic blip counts. |
| Portable UI parity | Same original configuration, identity-scoped state and conference theme on web and actual Binding host at compact/wide sizes. Assert participant/version/status/error text and actual action results, stale root/item refresh, accessibility, reachable Stop and review controls. Web has no active nearby scanner when unavailable. |

A practical first acceptance slice is two synthetic participants, one recorder, a synthetic transcript and local processing, proving participation → plan approval → stateful recording adapter stub → versioned review → exact private share → independent saved receipts. Label the stub explicitly. Then replace only the adapter with real device capture and repeat the safety/state tests plus two-device radio/Bridge checks. A synthetic journey can validate design; it is not a live recording demonstration.

Commands were read-only `rg --files`, `rg -n`, `nl`/`sed`, `cat`, Git status/ref/branch and ancestry checks. No tests were run. Source/existing test evidence is sufficient for a gap map and proposal, not readiness certification. Full code security review, source hashes, installed binary provenance, physical devices, active authority issuer and actual deployment remain outside this bounded slice.

Reusable learning for parent integration: retain three independent evidence axes in the OIW plan—portable renderer candidate, native nearby/hardware capability, and participant-authorized meeting lifecycle. None establishes the other.
